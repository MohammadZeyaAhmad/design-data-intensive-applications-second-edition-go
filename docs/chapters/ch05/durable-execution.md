# Chapter 5: Durable execution and replay

Packages: APP-07, C05-05, C08-08, C09-04 and C13-05. Compare the [persisted process manager](checkout-workflow.md) with the [Temporal profile](../../TEMPORAL.md). The shared business feature makes the scheduling difference visible without changing the meaning of a purchase.

Read these boundaries in order:

1. Ordering's checkout facade freezes a Catalog quote, chooses an engine and commits its dispatch intent with the accepted event. Retrying that request does not choose again.
2. `internal/checkout/adapters/temporal/workflow.go` records only deterministic scheduling commands. Workflow replay reconstructs those commands; it does not execute provider HTTP calls again.
3. `activities.go` loads a job, invokes the shared `advance` feature and saves progress. Activities can run more than once. Their successful results therefore have permanent logical-step receipts.
4. `internal/checkout/adapters/postgres/temporal.go` atomically saves each transition and receipt. Its lease token rejects an old completion, while cached results resolve completion loss.
5. `client.go` and the composition-root dispatcher bridge database intent to a stable Temporal execution. The start RPC and database acknowledgment are separate commits, so retry identity matters here too.

Try three schedules:

| Failure point | What survives | Recovery |
|---|---|---|
| Resource effect committed; activity checkpoint absent | Owner reservation/payment identity and job's old phase | Lease expiry followed by the same activity and resource IDs |
| Activity checkpoint committed; Temporal completion absent | Job's new phase and saved old-step result | Return that result, then schedule the next ordinal |
| Temporal start accepted; database acknowledgment absent | Existing stable workflow ID and pending start intent | Reject duplicate start, verify its type and acknowledge it |

`make integration` asserts these database boundaries, including a receipt insertion failure that rolls back the progress update. `make integration-temporal` uses a real server to stop SDK workers after each external stage, cancel a captured purchase, and replay an old history. Test workers deliberately expire their test leases to keep the stage matrix short. `make verify-temporal` separately kills real containers during a payment activity and waits for natural lease expiry.

The committed synthetic fixture `internal/checkout/adapters/temporal/testdata/checkout-v0.json` was generated by `legacyCheckout` in the real integration test. It includes a provider-response-loss retry and a durable one-second timer, without a version marker. The current workflow must replay it while new executions choose the versioned 500-millisecond loop. Editing a workflow's command order without a compatible branch can break replay even when ordinary happy-path tests pass.

Pause and cancellation demonstrate another boundary: a signal is only a hint. The database holds authoritative flags and an immutable operator audit. A delayed/duplicated wake cannot choose another tenant, unpause a job, change its quote or authorize a refund. Native cancellation continues in a disconnected context so it can execute the same source-outcome fence and resource closure. Termination offers no such cleanup.

This is durable execution with idempotent business effects. No scheduling engine makes an arbitrary external call exactly once. The provider simulator and owner records let the project demonstrate the required identities and reconciliation explicitly.
