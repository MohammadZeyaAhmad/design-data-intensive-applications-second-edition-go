# Replication and restore drill

Scope: the isolated C06-01 fixture. The executable controller performs these steps; production needs separately validated fencing, privileges, storage and recovery objectives. The fixture never accepts an arbitrary existing database URL.

1. Run `make replication-model replication-demo`. Retain `artifacts/replication/*.json` and `artifacts/replication-binaries/manifest.json`; check revision, dirty state and runtime. Each native run creates fresh temporary data and deletes it after owned processes stop.
2. Inspect each mode's primary/receive/replay LSNs and byte lag. Expect one acknowledged async probe lost under disconnected WAL transport and zero lost probes for the two synchronous modes. A paused replay process may still have durable received WAL. Do not classify that stale read as data loss.
3. For a planned role change, stop application admission and establish the old-primary fence first. In this fixture the controller kills its owned process group, waits for exit, checks the endpoint, and tests the still-running old API. If fencing is uncertain, promotion must stop. Neither a DNS change nor an epoch change in the new database proves the old database is fenced.
4. Promote the caught-up candidate. Advance the control-owned Inventory authority epoch and configure new API/worker incarnations with that token. Confirm old-token writes fail without stock, receipt or event effects. Confirm new-token writes succeed. Keep the old primary quarantined until actual rewind or a new snapshot; restart it only as a follower.
5. For an uncertain synchronous commit, inspect the durable command receipt and retry the same business intent after restoring transport. A deadline or missing HTTP reply does not prove rollback. A conflicting retry must not silently replace the original intent.
6. For logical corruption, preserve the damaged source and validate the base-backup manifest first. The fixture also proves a corrupted relation is rejected. Select the named restore point and required complete archived WAL. Restore into a separate empty owned directory and independent port; never restore over the current primary or its standby.
7. Wait for recovery to the selected target and promotion. Compare authoritative stock bounds/version, command receipt count and outbox count with the pre-error snapshot. Verify the before-target receipt exists, the after-target receipt is absent, and the real Atlas API reads the restored state. Record recovery-to-ready duration and the selected recovery window.
8. Review all assumptions before adopting a production recovery plan: slots and WAL retention limits, archive failures, fencing service, cross-context writers, offsite storage, encryption/access, key recovery, retention deletion, tablespaces, restore capacity and measured objectives. Those production obligations remain in the original OPS-03/P41 plan.

`docker compose -f deploy/compose/replication/compose.yaml -p ddia-go-replication down` removes the owned sandbox if a shell is interrupted. It has no persistent database volume. Native mode terminates owned process groups on cancellation; it never searches for or kills processes by a generic PostgreSQL name.
